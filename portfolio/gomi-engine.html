G.O.M.I Engine Game Object Modular Infrastructure Engine

学生時代の卒業制作として開発した、C++ / ECS（Entity-Component-System）ベースの2Dゲームエンジンです。 「ロジックを持たないデータとしてのComponent」「Componentの集合に対してのみ処理を行うSystem」 という原則を軸に、当たり判定・入力・描画・音声をそれぞれ独立したモジュールとして構成しています。 卒業後もエンジンとして手を入れ続けており、このドキュメントでは現在の設計と、 当時から変更した箇所を実装ベースでまとめています。

02 — Engineering Highlights

アピールポイント

「ECSを採用している」だけでなく、実際にどう実装しているかを、設計上の工夫とトレードオフも含めて紹介します。

01 / Component Storage

Sparse Set + SoA な ComponentArray

各ComponentはComponentArray<T>として、疎なentityToIndex （Entity ID→密配列index）と、実データの密配列componentsを分離して保持しています。 反復処理は密配列を先頭から舐めるだけなので、Component数が多いWorldでもキャッシュに乗りやすい構造です。

トレードオフ：EntityID用の疎配列はMAX_ENTITIESぶん確保するため、 Entity上限が大きくなるほどComponent型ごとのメモリ使用量も比例して増えます。
ComponentArray.h
template <typename T>
class ComponentArray
{
  std::vector<uint32_t> generations;
  std::vector<int> entityToIndex;  // 疎配列：Entity ID→index
  std::vector<int> indexToEntity;
  std::vector<T> components;       // 密配列：実データ
  int count = 0;
  // ...
};
02 / Removal Strategy

swap-remove による O(1) 削除

Componentの削除は末尾要素と入れ替えてからpop_back()する swap-removeを採用しています。要素をシフトしないため削除コストはO(1)で、 密配列は常に隙間なく詰まった状態を保てます。

トレードオフ：削除の度に配列内の要素順が入れ替わるため、 「挿入順を保持したい」用途には向きません（このエンジンでは順序に意味を持たせていません）。
ComponentArray.h — removeComponent
int lastIndex = components.size() - 1;
std::swap(components[lastIndex], components[entityToIndex[e.id]]);
std::swap(indexToEntity[lastIndex], indexToEntity[entityToIndex[e.id]]);
entityToIndex[indexToEntity[lastIndex]] = entityToIndex[e.id];

components.pop_back();
indexToEntity.pop_back();
entityToIndex[e.id] = -1;
03 / Handle Safety

Generationによるダングリング参照の構造的防止

Entity・UIHandleはどちらも { id, generation }の組で表現され、破棄のたびに世代番号をインクリメントします。 古いハンドルを保持したままアクセスしても、generationの不一致で「無効」と判定されるため、 解放済みスロットへの誤アクセスを型システムのレベルで防いでいます。

Entity.h
struct Entity
{
  unsigned int id;
  unsigned int generation;

  inline bool operator==(const Entity& other) const
  {
    return id == other.id && generation == other.generation;
  }
};
04 / Conflict Resolution

WorldEventBus — 移動リクエストの集約と一括解決

入力・AIなど複数の発生源が同じEntityへ移動を要求しうるため、MoveRequestEventを 一度WorldEventBusのEntity単位のキューに集約し、 MoveResolveSystemが優先度とブレンドモード（DIRECTIONAL / ADDITIVE）に基づいて 1つの移動量へ解決してから、X軸・Y軸を分離して壁判定を取ります。 「誰が動かすか」を早期に確定させず、フレーム末で一括解決することで競合を避けています。

MoveResolveSystem.cpp（抜粋）
for (auto& ev : it->second) {
  if (ev.blend == MoveBlend::DIRECTIONAL) {
    if (ev.priority > bestPriority) { finVec = ev.velocity; ... }
    else if (ev.priority == bestPriority) finVec += ev.velocity;
  } else if (ev.blend == MoveBlend::ADDITIVE) {
    addVec += ev.velocity;
  }
}
// X軸・Y軸を分離して壁を判定
auto hitX = world.col().queryAt(world, e, ..., { movec.result.x, 0 });
auto hitY = world.col().queryAt(world, e, ..., { 0, movec.result.y });
05 / Collision

空間分割グリッド + 軸分離による当たり判定

毎フレーム128×128pxのグリッドへCollisionComponent持ちのEntityを登録し、 判定時は自身が属するセルの周囲9マスだけを走査します。総当たりのO(n²)を避けつつ、 移動量をX/Y軸で分けて判定することで「壁に当たった軸だけ止める」滑るような挙動を実現しています。

トレードオフ：グリッドは毎フレーム再構築するため、Entity数が極端に多い場合は 構築コストが支配的になる可能性があります（現状の規模では問題になっていません）。

static constexpr Cell neighbors[9] = {

06 / Platform Boundary

IDrawer / IInput / IWindow / IAudioBackendによる抽象化

Game本体とECSコアは、これら4つの純粋仮想インターフェースにのみ依存し、 DxLib実装（DxWindow / DxDrawer 等）を直接参照しません。 メインループとゲームロジックはDxLibを知らない状態を保っています。

正直に：画像/音声の実ファイル読み込みを担うResourceManagerは DxLib.h（CreateGraphFromMem等）を直接呼んでおり、 エンジン全体が完全にDxLib非依存というわけではありません。抽象化できているのは 「メインループ・入出力・描画命令の発行」までです。
IDrawer.h / IWindow.h
class IDrawer {
public:
  virtual void init() = 0;
  virtual void drawImage(int handle, int x, int y, ...) = 0;
  virtual void present() = 0;
  virtual ~IDrawer() = default;
};
// 実装: DxDrawer / 差し替え可能

04 — From Graduation Work to Now

卒業制作からの進化

卒業制作時点で「動くこと」を優先して積み上がった構造的な負債を、卒業後にひとつずつ見直しました。 「言われて直した」ものではなく、実装しながら見えてきた課題に対して選んだ解決策です。

4.1

ComponentManagerの型消去化

課題：卒業制作時点のComponentManagerは、Component型ごとに専用メンバーを持ち、 addComponent / getComponentArray / releaseAll の3箇所にif constexprの分岐を手動で追加する必要がありました。型を1つ増やすたびに、 同じ形の分岐を3回コピーするだけの作業が発生していました。

Before
class ComponentManager {
  ComponentArray<TransformComponent> transformComponents;
  ComponentArray<RendererComponent> rendererComponents;
  // ...型の数だけ専用メンバー

  template <typename T>
  void addComponent(Entity e, T c) {
    if constexpr (std::is_same_v<T, TransformComponent>)
      transformComponents.addComponent(e, c);
    else if constexpr (...) // 以下続く
  }
};
After
template <typename T>
ComponentArray<T>& getOrCreate() {
  auto& slot = arrays[std::type_index(typeid(T))];
  if (!slot) slot = std::make_unique<Holder<T>>();
  return static_cast<Holder<T>&>(*slot).array;
}

template <typename T>
void addComponent(Entity e, T c) {
  getOrCreate<T>().addComponent(e, c);
}
Why — なぜこの設計にしたか

型ごとの分岐をコンパイル時に手で並べる方式は、型が増えるほどComponentManager.hという ひとつのファイルへの変更が集中し、無関係な変更のマージ競合も起きやすくなります。 std::type_indexによる実行時ディスパッチに切り替えることで、 型ごとの追加コストをゼロにできる一方、unordered_map経由のルックアップが 1段挟まる分、直接メンバーアクセスより僅かに遅くなるはずです。ここでは「型追加の容易さ」を 「理論上のルックアップ速度」より優先しました。

4.2

Systemファクトリの撤廃

課題：SystemTypeというenumと、それをswitchで実体化する createSystem()工場関数を使っていました。Systemを1つ追加するたびに、 クラス実装に加えてSystemType.h・SystemInclude.h・ SystemInclude.cppの3ファイルへの追記が必要でした。

Before
// SystemType.h
enum class SystemType : int {
  PlayerControlSystem, MoveSystem, PhysicsSystem, // ...
};

// SystemInclude.cpp
std::unique_ptr<ISystem> createSystem(SystemType type) {
  switch (type) {
    case SystemType::RendererSystem:
      return std::make_unique<RendererSystem>();
    // ...11ケース
  }
}
After
// ISystem.h
template <typename T>
std::function<std::unique_ptr<ISystem>()> System() {
  return []() { return std::make_unique<T>(); };
}

// 呼び出し側（StageDefinition構築時）
System<RendererSystem>()
Why — なぜこの設計にしたか

enum + switchは「このプロジェクトに存在する全System」を1箇所に列挙する強みがある一方、 Systemの実体（クラス）と識別子（enum値）を常に同期させ続ける手間が発生します。 テンプレートで直接std::make_unique<T>を呼ぶ工場関数を都度生成する方式にすることで、 識別子そのものをなくしました。トレードオフとして「今どんなSystemが存在するか」を一覧できる場所は無くなるため、 大規模化した場合はSystem一覧をドキュメント側（本ページの03章など）で補う必要があります。

4.3

Stage定義の文字列キー化とWorldChangeペイロード変更

課題：卒業制作時点はstageTableというintキーの 静的unordered_mapでステージ内容を管理しており、WorldChange イベントも「何番目のステージか」というintを直接やり取りしていました。 UIボタン側にステージ番号がベタ書きされ、登録順が変わると壊れる構造でした。

Before
// Stage.cpp
const std::unordered_map<StageID, StageDef> stageTable = {
  { 0, { 0, { SystemType::RendererSystem }, {}, {{"Title", {0,0}}} }},
  { 1, { 1, { /* ... */ }, { /* Player等 */ }, {} }},
};

// UIPrefab_Title.cpp（ボタン側）
EventBus::getInstance().emit<int>("WorldChange", 1); // 1固定
After
// Stage_Field.cpp（データとして直接記述）
const StageDefinition Stage_Field = { "Field", { /* ... */ }, { /* ... */ }, {} };

// main()
game.addWorld(Stage_Title);
game.addWorld(Stage_Field);

// UIPrefab_Title.cpp（ボタン側）
EventBus::getInstance().emit<std::string>("WorldChange", "Field");
Why — なぜこの設計にしたか

数値の登録順に依存する設計は、途中にステージを1つ挿しただけで既存の遷移が壊れる、という事故が起きやすい形でした。 登録名をそのまま切り替え先の指定に使えるようにしたことで、「何番目か」を意識する必要が無くなりました。 引き換えに、文字列の打ち間違いは実行時までコンパイラが検出できません（"Feild"のような typoはworldNames.at()の例外として実行時に発覚します）。数値キーの静的な安全性と、 名前ベースの保守しやすさのどちらを取るかで、後者を選びました。
